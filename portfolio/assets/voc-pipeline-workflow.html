VOC Report Pipeline

How we generate more consistent, more trustworthy Voice of Customer reports — from raw feedback to stakeholder delivery

Pipeline at a Glance

7 Pipeline Steps
3 Quality Lenses
8 AI Review Passes
4 Reconciliation Statuses

The Problem We're Solving

LLM-generated reports drift over time. The same data can produce different narratives each run. If we feed a previous report into context, the model copy-pastes hallucinations. If we don't, we lose continuity and can't track trends.

Our approach: generate fresh (with no memory), adversarially review for accuracy, then reconcile against previous findings. This helps break the copy-paste loop while preserving temporal tracking and reducing the chance that hallucinations become "facts."

Before the Pipeline Runs

🛡 Upstream Model Monitoring

Before any report is generated, we continuously monitor the enrichment model for behavioral drift:

  • Reasoning token usage — Has the model started using more or fewer reasoning tokens than expected? Sudden shifts indicate prompt sensitivity or capability changes.
  • Classification stability — Are theme/severity distributions shifting without corresponding data changes?
  • Latency & error rates — Operational health checks ensure the model is responding within expected bounds.
  • Drift alerts — Automated flags trigger when any metric deviates beyond thresholds, pausing pipeline execution until reviewed.

⚙ Enrichment Model

Raw member feedback is enriched before it reaches the report pipeline. The enrichment model handles:

  • Theme classification — Each piece of feedback is tagged with one or more themes from the Journey Framework taxonomy.
  • Severity scoring — Feedback is classified by impact: Critical Blocker, Major Inconvenience, Minor Inconvenience, Suggestion, or No Action.
  • Sentiment analysis — Positive, neutral, or negative tone detection provides emotional context.
  • Quote extraction — Verbatim quotes are identified and preserved for evidence traceability.

These upstream checks ensure the data entering the pipeline is high-quality and the model behavior is stable before we generate any stakeholder-facing reports.

Pipeline Steps

1
Pass 1

Generate a Fresh Report

The model analyzes the current period's member feedback with zero memory of previous reports. It produces findings, recommendations, and impact assessments based purely on what the data shows right now.

This deliberate "amnesia" prevents the model from perpetuating earlier mistakes or carrying forward stale conclusions. Every report starts from a clean slate.

2
Pass 2

Adversarial Quality Review

Before anything reaches stakeholders, the fresh report is scrutinized through three independent review lenses running in parallel:

📊

Data Fidelity

Are the numbers right? Can every quote be traced to source data? Are trend assertions supported?

🧠

Epistemic Humility

Is the model overstating? Confusing correlation with causation? Leaking bias into conclusions?

🎯

Actionability

Could a PM act on these recommendations? Are owners identified? Is severity proportionate to evidence?

The three reviews are synthesized into a single revised set of findings. Conflicts are resolved by these rules:

✅ Passes All 3 Lenses Keep or strengthen the finding
⚠ Fails 1 Lens Hedge with qualifiers ("likely," "suggests")
❌ Fails 2+ Lenses Cut entirely or replace with data-supported assertion
3
Pass 3

Extract Verified Assertions

Every factual assertion in the reviewed report is extracted into a structured record — the specific assertion, its confidence level, its evidence source, and where it maps to the Member Journey Framework.

Because assertions are extracted from the reviewed report (not the raw draft), hallucinated assertions are more likely to be caught and removed before they enter the temporal record. This helps protect long-term data integrity.

4
Pass 4

Reconcile with Previous Findings

This period's assertions are compared assertion-by-assertion against the previous period. Each assertion receives a reconciliation status:

CONSISTENT — stable (<5% variance) CHANGED — shifted (>10% variance) NEW — first appearance REMOVED — no longer supported

The reconciliation injects temporal context into the final report: "This issue persists from last quarter" or "This is a newly emerging concern." Stakeholders get continuity without copy-paste drift.

For the very first report in a series, this step is skipped — there's nothing to reconcile against yet.

5
Pass 5

Generate Internal Change Log

A human-readable change log summarizes what shifted between periods: which issues escalated, which were resolved, and where new concerns surfaced. This is an internal artifact for the research team to review before the final report goes out.

6
Outputs

Deliver & Archive

The pipeline produces four artifacts, split between stakeholder delivery and internal audit:

📄 Final Report

The stakeholder-facing deliverable with temporal context, verified assertions, and qualified recommendations.

📋 Change Log

Period-over-period summary of what shifted, for internal review before distribution.

🗄 Assertions Record

Structured JSON of every verified assertion — stored for next period's reconciliation step.

🔍 Reconciliation Detail

assertion-by-assertion comparison for audit trail. Shows exactly what changed and why.

Built-In Safeguards

🚫 Hallucination Mitigation

  • Fresh generation with no prior report context helps break the copy-paste loop
  • Three-lens adversarial review is designed to catch fabricated statistics before they become assertions
  • Assertions extracted only from reviewed output, reducing the risk of unverified assertions persisting

📈 Temporal Integrity

  • Reconciliation uses stable identifiers to track the same issues across reporting periods
  • Automated warnings flag when nothing appears consistent between periods — a sign something may have shifted in the data or model
  • 12+ periods of assertion history maintained for longitudinal tracking
