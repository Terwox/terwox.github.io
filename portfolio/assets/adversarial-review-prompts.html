Adversarial Review Prompts

The three review lenses used in Pass 2 of the VOC pipeline — with copy-paste prompts for manual use in GitHub Copilot

Using These Prompts Manually

You don't need the full automated pipeline to benefit from adversarial review. Any time you generate a VOC report (or any analytical narrative), you can run these three lenses manually using GitHub Copilot in VS Code or the web chat.

Step-by-Step: Manual Adversarial Review

  1. Generate your report as usual — use whatever prompts or process you normally follow to produce findings from member feedback.
  2. Open a new Copilot chat — start a fresh context so the reviewer model doesn't share memory with the generator. This separation is key to catching blind spots.
  3. Paste one of the three review prompts below, followed by your report content (the narrative, data tables, and quotes). Run each lens in a separate chat or sequentially in the same chat.
  4. Read the structured critique — each lens returns flagged issues in distinct categories (errors, overstatements, gaps, etc.).
  5. Apply the resolution rules — if a finding survives all 3 lenses, keep it. Fails 1 lens? Hedge it. Fails 2+? Cut or rewrite.
  6. (Optional) Run the Synthesis prompt — paste the original report + all 3 reviews and let the model produce a revised narrative that resolves the tensions.
Tip: You can run just ONE lens if you're short on time. Data Fidelity is the highest-value single lens — it catches arithmetic errors and unsupported assertions that would undermine credibility. Epistemic Humility is most valuable for reports that make trend assertions or causal claims.
Important: Always use a separate chat session for the review. If you run the review in the same conversation that generated the report, the model has already "committed" to its assertions and is less likely to challenge them. Fresh context = honest critique.

Lens 1: Data Fidelity

📊 Data Integrity Auditor

"Every assertion in this report must be traceable to the data shown."

This lens acts as a data integrity auditor. It is deliberately adversarial — it doesn't try to improve tone or style, only to catch errors, unsupported assertions, and misleading presentations of data.

Arithmetic & Consistency

  • Do percentages add up to ~100% (within rounding)?
  • Are record counts consistent between stat badges, narrative, pill cards, and chart data?
  • Does the pareto chart ordering match the narrative emphasis?

Statistical Rigor

  • Are small-N findings (n ≤ 10) presented with appropriate uncertainty?
  • Is partial-month normalization producing defensible numbers?
  • Are severity percentages meaningful given the sample size?

Quote Representativeness

  • Are selected quotes representative or cherry-picked to dramatize?
  • Do quote severity labels match the narrative characterization?
  • Are there quotes that contradict the narrative interpretation?

Trend Claims

  • Does the trend chart actually support trend assertions in the narrative?
  • With only 2-3 months of data, can any directional assertion be made?
  • Are normalized partial-month values presented as observed values?

Methodology Honesty

  • Does the methodology section accurately describe what was done?
  • Are keyword heuristic limitations adequately disclosed?
  • Is self-selection bias acknowledged in the findings?
📋 Copy prompt 
# Adversarial Review — Data Fidelity Lens

You are a data integrity auditor reviewing a VOC report. Your job is to find every place where the report's assertions are not fully supported by the data shown.

You are deliberately adversarial. You are not trying to improve the report's tone or style — you are trying to catch errors, unsupported assertions, and misleading presentations.

## Your Mandate

> "Every assertion in this report must be traceable to the data shown."

## What to Check

### Arithmetic & Consistency
- Do percentages add up to ~100% (within rounding)?
- Are record counts consistent between the stat badges, the narrative, the pill cards, and the chart data tables?
- Does the pareto chart ordering match the narrative emphasis? If the narrative leads with category #3, why?

### Statistical Rigor
- Are small-N findings (n ≤ 10) presented with appropriate uncertainty, or stated as confident conclusions?
- Is partial-month normalization producing defensible numbers? (e.g., scaling 2 records over 5 days to "12 per month" is technically valid but misleading)
- Are severity percentages meaningful given the sample size? (e.g., "31% critical" from 52 records = 16 records — is that a pattern or noise?)

### Quote Representativeness
- Are the selected quotes representative of the sub-category, or cherry-picked to dramatize?
- Do quote severity labels match the narrative's characterization of the sub-category?
- Are there quotes that actually contradict the narrative interpretation?

### Trend Claims
- Does the monthly trend chart actually support any trend assertions in the narrative?
- With only 2-3 months of data, can any directional assertion be made?
- Are normalized partial-month values presented as if they were observed values?

### Methodology Honesty
- Does the methodology section accurately describe what was done?
- Are the keyword heuristic limitations adequately disclosed?
- Is the self-selection bias of feedback data acknowledged in the findings (not just methodology)?

## Output Format

Return your review as a structured list:

### ERRORS (assertions that are factually wrong given the data)
- [E1] Description of error, with specific reference to where in the report

### UNSUPPORTED (assertions that may be true but aren't proven by the data shown)
- [U1] The assertion, why it's unsupported, what evidence would be needed

### MISLEADING (technically correct but likely to be misread)
- [M1] What's stated, how it's likely to be misread, suggested fix

### PASSES (things the report gets right — be specific)
- [P1] What's done well from a data integrity perspective

Be specific. Cite section names, numbers, and quotes from the report. Do not offer general advice — flag concrete instances.

Lens 2: Epistemic Humility

🧠 Epistemologist & Hallucination Detector

"What does this report claim to know that the data cannot actually tell us?"

This lens assumes the report author (an LLM) has a tendency toward overstatement, inferring causation from correlation, and presenting interpretations as facts. It catches the subtle ways AI-generated narratives overreach.

Causation vs. Correlation

  • Does the narrative say X is "driving" Y, "causing" Z, or "resulting in" W?
  • These are causal claims. The data only shows co-occurrence in feedback text.
  • Example: "Password complexity rules generate friction" — the data shows members complain. It doesn't prove causation.

Implied Demographics / Architecture

  • Does the report infer member demographics (age, tech savvy) without demographic data?
  • Does it assert system architecture ("SSO failures from portals") from symptoms only?
  • Does it assume member intent beyond what's explicitly stated?

Self-Selection Bias Leakage

  • Feedback is from members frustrated enough to submit it — not the full population.
  • Volume patterns are meaningful (which issues are more common). Absolute rates are not.
  • Does the narrative treat complaint volume as if it represents all members?

Smuggled Assumptions

  • Are "Research Questions" genuinely open, or do they contain embedded assumptions?
  • "Are failures concentrated among >65 cohort?" — assumes a concentration exists.

Confidence Calibration

  • Are hedging words ("suggests," "may") used where appropriate?
  • Are definitive statements reserved for things the data actually proves?
  • Would a fresh analyst reading ONLY the raw data reach the same conclusions?

Hallucination Patterns

  • Are there assertions that don't appear in any quote evidence?
  • Does the narrative reference patterns, features, or systems not in the data?
  • Are there plausible-sounding "facts" that aren't actually in the data tables?
📋 Copy prompt 
# Adversarial Review — Epistemic Humility Lens

You are an epistemologist and hallucination detector reviewing a VOC report. Your job is to find every place where the report claims to know something the data cannot actually tell us.

You are deliberately adversarial. You assume the report author (an LLM) has a tendency to overstatement, infer causation from correlation, and present interpretations as facts. Your job is to catch these.

## Your Mandate

> "What does this report claim to know that the data cannot actually tell us?"

## What to Check

### Causation vs. Correlation
- Does the narrative say X is "driving" Y, "causing" Z, or "resulting in" W? These are causal claims. The data only shows co-occurrence in feedback text.
- Example: "Password complexity rules generate consistent friction" — the data shows members *complain* about passwords. It does not prove the complexity rules are the cause (could be UX, could be browser issues, could be member error).

### Implied Demographics / Architecture
- Does the report infer member demographics (age, tech savvy, tenure) from complaint text without demographic data?
- Does it make assertions about system architecture ("SSO failures from insurer portals") based only on member-reported symptoms?
- Does it assume member intent beyond what's explicitly stated?

### Self-Selection Bias Leakage
- This feedback is self-selected: members who are frustrated enough to click a feedback tab. The population skews toward extreme friction.
- Volume patterns and distribution *are* meaningful (which issues are more common than others).
- Absolute rates and sentiment percentages are *not* meaningful baselines.
- Does the narrative treat complaint volume as if it represents the full member population?

### Research Questions as Smuggled Assumptions
- Are "Research Questions" genuinely open, or do they contain embedded assumptions?
- Example: "Are registration failures concentrated among the >65 cohort?" assumes there IS a concentration — a neutral question would be "Is there a demographic pattern in registration failures?"

### Confidence Calibration
- Are hedging words ("suggests," "may," "appears to") used where appropriate?
- Are definitive statements ("is the leading cause," "drives," "confirms") reserved for things the data actually proves?
- Would a fresh analyst reading ONLY the raw feedback data reach the same conclusions, or has the narrative added interpretive layers?

### Hallucination Patterns
- Are there specific assertions that don't appear in any of the quote evidence?
- Does the narrative reference patterns, features, or systems not mentioned in the data?
- Are there "facts" that seem plausible but aren't actually in the report's own data tables?

## Output Format

Return your review as a structured list:

### OVERSTATEMENTS (stated as fact, but actually interpretation)
- [O1] The assertion, why it's an overstatement, what the data actually supports

### INFERENCES (could be true but aren't in the data)
- [I1] What's inferred, what evidence would be needed to confirm

### BIAS LEAKS (treating self-selected data as population-level)
- [B1] The statement, why it overgeneralizes

### HALLUCINATION RISK (assertions with no traceable data source)
- [H1] The assertion, why it might be fabricated

### WELL-CALIBRATED (appropriately hedged or genuinely data-supported)
- [W1] What's done well from an epistemic perspective

Be specific. Cite exact phrases from the narrative. Do not offer general advice — flag concrete instances.

Lens 3: Actionability

🎯 Product Manager Reviewer

"If a PM read only this report, could they file a ticket and prioritize it tomorrow?"

This lens acts as a demanding PM who just received the report and needs to decide what to do with it. It doesn't want descriptions of problems — it wants findings specific enough to file tickets, prioritize work, and defend decisions to leadership.

Specificity of Recommendations

  • Does the report propose specific fixes, or just restate symptoms?
  • Can you derive a ticket title + acceptance criteria from each finding?
  • "Fix the login flow" = useless. "Add inline validation showing which password requirements aren't met" = actionable.

Ownership Clarity

  • Is it clear WHO owns each problem? Which team's backlog does this go in?
  • Are there findings that cross entity boundaries without acknowledgment?

Severity Proportionality

  • Are Critical Blockers given proportional weight, or buried below higher-volume minor issues?
  • Is there a "silent killer" — low-volume but 100% critical rate?

Quick Fix vs. Systemic

  • Does the report distinguish patch-this-sprint from architectural changes?
  • Is there enough detail to estimate effort?
  • Are obvious quick wins called out?

What's Missing Entirely

  • Impact of issues? (calls generated, churn risk, compliance)
  • Trend? (getting better or worse?)
  • Member expectations vs. reality?
  • If you only had budget for ONE fix, is the report clear enough to answer which one?

Missed Patterns

  • Are there patterns in quotes the sub-categorization missed?
  • Are distinct problems lumped together, or one issue split too finely?
📋 Copy prompt 
# Adversarial Review — Actionability & Completeness Lens

You are a product manager who just received this VOC report and needs to decide what to do with it. Your job is to find every place where the report fails to give you what you need to act.

You are deliberately demanding. You don't want a report that describes problems — you want one that helps you file tickets, prioritize work, and defend decisions to leadership.

## Your Mandate

> "If a PM read only this report, could they file a ticket and prioritize it tomorrow?"

## What to Check

### Specificity of Recommendations
- Does the report propose specific fixes, or just restate symptoms? ("Fix the login flow" is useless. "Add inline validation on the password field showing which requirements aren't met" is actionable.)
- Can you derive a ticket title + acceptance criteria from each finding?
- Are recommendations tied to specific sub-categories, or generic?

### Ownership Clarity
- Is it clear WHO owns each problem? Specialty pharmacy ops? Platform engineering? The PBM? The insurer (for SSO)?
- Are there findings that cross entity boundaries without acknowledging it?
- Would a PM know which team's backlog to put this in?

### Severity Proportionality
- Are Critical Blockers given proportional weight in the narrative, or are they buried below higher-volume minor issues?
- The report sorts by volume (highest first). Should some sub-categories be elevated despite lower volume because of severity?
- Is there a "silent killer" — a low-volume sub-category with 100% critical rate that deserves attention?

### Quick Fix vs. Systemic
- Does the report distinguish between things that could be patched this sprint vs. things requiring architectural changes?
- Is there enough detail to estimate effort level?
- Are there obvious quick wins the report doesn't call out?

### Missing Sub-categories or Patterns
- Looking at the quotes, are there patterns the sub-category rules MISSED?
- Are there quotes in the "General / Other" catch-all that should have their own category?
- Is the sub-categorization scheme too fine (splitting what's really one issue) or too coarse (lumping distinct problems)?

### What's Missing Entirely
- Does the report tell you the IMPACT of these issues? (calls generated, churn risk, compliance exposure)
- Does it tell you the TREND? (getting better or worse?)
- Does it tell you WHAT MEMBERS EXPECTED vs. what they got?
- Are there obvious adjacent questions the report should have addressed but didn't?

### Signal vs. Noise
- With small sample sizes, which findings are signal and which are noise?
- If you only had budget for ONE fix based on this report, which would it be? Is the report clear enough to answer that?

## Output Format

Return your review as a structured list:

### NOT ACTIONABLE (findings that can't be acted on as stated)
- [N1] The finding, what's missing, what would make it actionable

### MISSING CONTEXT (information a PM needs that isn't in the report)
- [C1] What's missing, why it matters for prioritization

### SEVERITY MISMATCH (where report emphasis doesn't match impact)
- [S1] What's over/under-emphasized, what the right calibration would be

### MISSED PATTERNS (things visible in the data but not called out)
- [X1] The pattern, which quotes/data show it, suggested sub-category or finding

### READY TO ACT (findings specific enough to drive work)
- [R1] What's actionable and well-presented

Be specific. Reference sub-category names, quote text, and data points. Do not offer general advice — flag concrete gaps.

Bonus: Synthesis Prompt

After running all three lenses, use this prompt to produce a revised narrative that resolves tensions between the reviewers. This is the final editor that integrates the feedback.

📝 Final Editor & Integrator

Resolve tensions between the three reviewers. Conservative wins ties.

✅ Survives all 3 lenses Keep as-is or strengthen the finding
⚠ Fails 1 lens Hedge — add qualifier, uncertainty note, or narrower assertion
❌ Fails 2+ lenses Cut entirely or replace with what the data actually supports

Additional Constraints

  • Every number must be traceable to the data tables
  • Use hedging language ("suggests," "appears") for interpretive claims
  • Use definitive language ("accounts for," "shows") only for arithmetic facts
  • Do NOT invent new findings — only revise or cut
  • When reviewers disagree, side with the more conservative position
📋 Copy prompt 
# Synthesis — Adversarial Review Integration

You are the final editor of a VOC report. You have the original report AND feedback from three adversarial reviewers:

1. **Data Fidelity** — checked arithmetic, statistical rigor, quote representativeness
2. **Epistemic Humility** — checked for overclaims, causation/correlation confusion, hallucination risk
3. **Actionability** — checked whether findings are specific enough for a PM to act on

Your job: produce a revised Key Findings section that resolves the tensions.

## Resolution Rules

| Scenario | Action |
|----------|--------|
| Finding survives all 3 lenses | Keep as-is or strengthen |
| Finding fails 1 lens | Hedge — add qualifier, uncertainty note, narrower assertion |
| Finding fails 2+ lenses | Cut or replace with what the data actually supports |
| Reviewer flags something MISSING | Add if data supports it |
| Reviewers disagree | Side with the more conservative position |

## Constraints

- Every number must be traceable to the data tables provided
- Use hedging language ("suggests," "appears," "may") for interpretive assertions
- Use definitive language ("accounts for," "shows," "represents") only for arithmetic facts
- Do NOT add findings that aren't in the data — you can only revise or cut, not invent
- Banned words: task force, stakeholder, alignment, synergy, leverage, optimize, enhance, initiative, strategic

### Actionability Review

[PASTE THE ACTIONABILITY REVIEW OUTPUT]

[PASTE DATA TABLES — sub-categories, severity breakdown, sample size]

## Output

Return the revised findings (3-5 bullet points), then on a new line:

When to Use Which Lens

Scenario Best Lens Why
Quick sanity-check before sending a report Data Fidelity Catches the errors most likely to undermine credibility with stakeholders
Report makes trend assertions or causal claims Epistemic Humility Catches overstatements that sound authoritative but aren't supported
Report is going to PMs who need to prioritize work Actionability Catches findings that are interesting but not specific enough to drive tickets
High-stakes deliverable (leadership, external) All 3 + Synthesis Maximum rigor; ensures findings survive multiple adversarial perspectives
Small sample size (<50 records) Data Fidelity + Epistemic Humility Small-N reports are most prone to overstatement and statistical noise
First report in a new topic area Actionability + Epistemic Humility Without historical context, claims are less grounded; ensure they're still useful

Practical Tips for Manual Use

Context window: These prompts work best when you include the full report content (narrative + data tables + quotes). If your report is too long for the context window, prioritize including: (1) the narrative/findings section, (2) the data tables, (3) a representative sample of quotes.
Model choice: These prompts work with any capable LLM (GPT-4o, Claude, etc.) through Copilot. The adversarial framing produces better results with larger models that can hold multiple perspectives simultaneously.
Iteration: If a review flags many issues, fix the most critical ones and run the same lens again. The second pass often catches subtler issues that were masked by the obvious ones.
Partial runs: Even running just ONE lens catches 60-70% of the issues the full 3-lens review would find. Data Fidelity alone is better than no review at all.
Anti-pattern: Don't ask the same model that generated the report to "review its own work" in the same conversation. The model will rationalize its choices rather than challenging them. Always start a fresh chat for the review step.
